# 更新记录规范（固定要求）

本文件是更新说明的**唯一格式规范**。写任何更新说明（changelog / 应用内弹窗 / GitHub Release）必须先符合本文件；与其它文档冲突时，以本文件为准。

流程类内容（版本号判定、跨端配置同步、发版步骤）见 [版本发布与更新记录维护指南](../版本发布与更新记录维护指南.md)。

---

## 1. 强制原则

1. **单一权威源**：完整内容只写在 `docs/版本记录/changelog.md`。
2. **同源派生**：弹窗与 GitHub Release 更新说明必须与 changelog 用户可见条目同口径，禁止另写一套。
3. **禁止别名**：分类名称、顺序、tone 不得改写或自创。
4. **只写已交付**：未验证、未发布的内容不得写入。

---

## 2. 强制词表

### 2.1 用户可见（changelog / 弹窗 / GitHub Release）

| 顺序 | 分类 | 弹窗 `tone` | 含义 |
|:----:|------|-------------|------|
| 1 | 新增 | `pink` | 新能力、新入口 |
| 2 | 优化 | `blue` | 体验、交互、性能改进 |
| 3 | 修复 | `yellow` | 缺陷修复 |
| 4 | 发布 | `yellow` | 版本升级、安装包交付 |

- 顺序固定：新增 → 优化 → 修复 → 发布。
- **无内容的分类整节省略**，不要留空标题。
- tone **强制映射**：`新增=pink`、`优化=blue`、`修复=yellow`、`发布=yellow`。禁止混用（例如修复不得用 `pink`）。

### 2.2 工程附录（仅 changelog）

| 分类 | 含义 |
|------|------|
| 版本与打包 | 跨端版本号、`versionCode`、产物文件名与 SHA256 |
| 验证 | 真实执行过的测试/构建命令与结果 |

工程附录**不得**进入弹窗或 GitHub Release 更新说明。

### 2.3 禁止别名（出现即改写）

| 禁止 | 改为 |
|------|------|
| 新增功能 / 基础功能 | 新增 |
| 改进 | 优化 |
| Bug 修复 | 修复 |
| 版本号统一 | 版本与打包 |
| 构建产物 | 并入 版本与打包 |
| 工程改进 / 技术细节 / 技术栈升级 / 已知情况 / 已知风险 | 并入 验证 或 版本与打包 |
| Highlights（作为分类名） | 不再使用；用 新增/优化/修复/发布 分节 |

## 3. 三出口固定模板

### 3.1 changelog（权威源）

文件：`docs/版本记录/changelog.md`，新版本插入到**文件顶部**（文档说明之后）。

```md
## v<版本号> (YYYY-MM-DD)

> 记录依据：`v<上一版本>` 发布提交 `<sha>` 之后的变更（建议保留）。

### 新增

- **能力名称**：用户可感知的结果与影响。

### 优化

- **优化名称**：说明体验或行为变化。

### 修复

- **问题名称**：说明修复的场景与结果。

### 发布

- 版本号统一升级至 `<版本号>`；发布 Windows Setup 安装包。

### 版本与打包

- 主应用、PC Tauri、Android、NSIS 安装器和安装器壳统一升级至 `<版本号>`。
- Android `versionCode` 从 `<旧值>` 递增至 `<安卓版本码>`（若本版有 Android 产物）。
- 已完成 PC 端核心安装包构建：
  - `PromptImageManager-Setup-<版本号>.exe`：<字节> 字节（<MB> MB），SHA256 `<哈希>`

### 验证

- `实际执行的命令`：通过，填写真实测试数量或构建结果。
```

条目写法：`- **短名**：用户结果优先的一句话；避免堆砌内部文件路径（工程细节可放验证/版本与打包）。

### 3.2 应用内弹窗

文件：`src/js/release/release-notes-data.js`，数组**首项**为当前版本，新到旧排序。

```javascript
{
    version: '<版本号>',
    date: 'YYYY-MM-DD',
    sections: [
        {
            title: '新增',
            tone: 'pink',
            items: ['面向用户的简短说明。']
        },
        {
            title: '优化',
            tone: 'blue',
            items: ['面向用户的简短说明。']
        },
        {
            title: '修复',
            tone: 'yellow',
            items: ['面向用户的简短说明。']
        },
        {
            title: '发布',
            tone: 'yellow',
            items: ['版本号统一升级至 vX.Y.Z；发布 Windows Setup 安装包。']
        }
    ]
}
```

文案约束：

- 简短、以用户结果为中心。
- **不写**：内部文件名、测试数量、构建命令、SHA256、未交付内容。
- 必须同时满足：`meta[name="version"]` == `RELEASE_NOTES[0].version`。

### 3.3 GitHub Release

由 `scripts/publish_release.ps1` **自动生成**，禁止手工另写一份分类。

```md
## PromptImageManager v<版本号>

### Downloads

| Asset | Size | SHA256 |
| --- | ---: | --- |
| `PromptImageManager-Setup-<版本号>.exe` | <MB> MB | `<哈希>` |
| `latest.json` | <MB> MB | `<哈希>` |

### 新增

- 与弹窗同源条目。

### 优化

- 同上。

### 修复

- 同上。

### 发布

- 同上。

> Full changelog: `docs/版本记录/changelog.md` in this repository.
```

- 数据源：`release-notes-data.js` 当前版本（与弹窗一致）。
- 分类顺序与词表同 §2.1；无条目整节省略。
- 哆嗦明细（验证命令、多产物哈希列表）只留 changelog。

---

## 4. 索引摘要

文件：`docs/版本记录/README.md`

- 只保留最新数条，一句话摘要。
- 不写校验和、不写「已创建 GitHub Release」等未完成声明。
- 最新版本必须与 `package.json` version 一致。

---

## 5. 每次写更新说明的检查清单

复制本清单，逐项勾选后再提交：

- [ ] changelog 顶部已插入 `## vX.Y.Z (日期)`，仅使用：新增 / 优化 / 修复 / 发布 / 版本与打包 / 验证
- [ ] 无禁止别名标题
- [ ] `release-notes-data.js` 首项已添加当前版本，分类与 tone 符合映射表
- [ ] 弹窗文案无内部细节（文件名/测试数/哈希/命令）
- [ ] `docs/版本记录/README.md` 最新版本摘要已更新
- [ ] `package.json` / `meta[name=version]` / `RELEASE_NOTES[0].version` 三方一致
- [ ] GitHub Release 正文由脚本生成，或已用 `scripts/gen_release_body.py` 生成后回填，未手写第二套分类
- [ ] 未把工程附录（版本与打包明细、验证）写进弹窗或 Release 更新说明

---

## 6. 工具入口

| 工具 | 用途 |
|------|------|
| `scripts/publish_release.ps1` | 发版：版本一致性校验 + 自动生成 Release 完整分节 |
| `scripts/gen_release_body.py` | 按弹窗数据生成 Release 正文 Markdown |
| `scripts/backfill_release_notes.py` | 回填历史 Release 正文 |
| `scripts/normalize_changelog.py` | 规范化 changelog 历史章节词表 |

---

## 7. 变更本规范

- 修改词表、模板或检查清单时，**必须同时**更新：本文件、`docs/工程指南/版本发布与更新记录维护指南.md` 中的交叉引用、`scripts/publish_release.ps1` 中的分节顺序（若涉及）。
- 不得只改某一个出口的实现而不同步本文件。
