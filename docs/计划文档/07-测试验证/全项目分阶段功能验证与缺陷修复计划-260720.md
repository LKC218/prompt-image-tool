## 一、目标

以真实用户操作为主线，完成全项目分阶段回归：所有页面、页面内所有可操作按钮与快捷键均须具备可追溯的测试项；发现缺陷后按统一分级修复、复测，并将高频路径沉淀为自动化测试。

### 量化完成标准

- 完成 PC 与移动端共 12 个核心页面、PC 详情弹窗及启动应用壳的测试记录。
- 每个页面的核心按钮均覆盖成功、失败或取消、重复操作与状态刷新；不具备测试前置条件的控件必须明确记录阻塞原因。
- 自动化基线与生产构建均有可追溯结果；已确认的 P0/P1 缺陷均完成修复、定向复测与受影响回归。
- 形成一份脱敏测试记录、缺陷清单和下轮未完成项，且文档入口已同步至代码地图。

### 智能体协作与同步机制

| 角色 | 专属子目标 | 独立范围 | 交付内容 |
|---|---|---|---|
| 基线验证智能体 | 验证自动化、构建、启动和路由基线 | 测试命令、应用启动与全局入口 | 命令结果、启动证据、P0/P1 候选 |
| 内容页验证智能体 | 验证双端首页、提示词库和详情按钮 | 首页、库页、详情及 PC 详情弹窗 | 控件结果、复现步骤、浏览器证据 |

- 移动剩余页面复验：浏览器自动化在访问 `?ui=mobile` 时出现 WebView 就绪超时，无法创建可交互移动会话；详情、分类与设置的本轮复验未执行。该现象尚无应用错误、页面日志或源码证据，不判定为产品缺陷，待稳定移动浏览器会话或 Android 环境复测。
- 后续 PC 编辑与分类复验：浏览器自动化连续三次无法取得页面结构，均返回“WebView is not ready yet”；未盲点或猜测坐标，未确认新的产品缺陷。该环境阻塞与移动端 WebView 超时共同导致剩余页面矩阵无法继续。

本计划不预设具体缺陷结论。所有缺陷必须在测试执行中以复现步骤、日志或截图为证据确认后再修复，避免为“修复”而引入无关改动。

### 验收原则

1. 同一业务能力必须至少验证 PC 与移动端各一次；受容器能力影响的功能还须验证 Tauri 或 Android 真机。
2. 每个按钮至少验证可见性、可点击性、成功结果、失败反馈和重复操作安全性；破坏性按钮额外验证确认与取消分支。
3. 每次修复遵循“复现失败 → 最小修复 → 定向复测 → 受影响页面回归 → 自动化补测”的闭环。
4. 使用独立测试数据，不记录真实用户提示词、图片、局域网地址、设备信息、访问令牌或导出备份文件。
5. 以系统绝对时间记录测试开始、结束与日志时间；不通过累计等待推断异步操作完成。

### 阶段 2：逐页按钮功能矩阵

**目标：** 逐一验证页面内所有可点击控件；以“控件清单”为唯一执行依据，禁止只走主流程。

#### 2.1 每个按钮的统一断言

| 检查维度 | 通过标准 |
|---|---|
| 可达与状态 | 按钮可见、文案或图标含义清晰、禁用条件正确、焦点顺序合理 |
| 成功路径 | 单次操作触发预期状态、页面跳转、数据写入或文件结果 |
| 失败路径 | 输入、权限、网络或存储失败时给出可行动提示，数据不被意外破坏 |
| 幂等与防抖 | 快速连点、重复提交或重复打开不产生重复数据、异常弹层或崩溃 |
| 关闭与撤销 | 菜单、弹层和确认框可取消；取消后数据和焦点保持正确 |
| 跨端一致性 | 同名能力在 PC / 移动端具有等价结果；允许布局不同，不允许语义不一致 |

**目标：** 验证浏览器界面无法覆盖的真实持久化、文件系统与原生能力。

### 阶段 4：缺陷修复与回归闭环

| 步骤 | 执行要求 |
|---|---|
| 缺陷登记 | 记录编号、端类型、版本、页面、控件、前置数据、精确步骤、实际结果、期望结果、证据和严重级别 |
| 根因定位 | 优先定位事件绑定、路由、状态同步、存储边界、容器桥接或样式层级；不以隐藏错误或增加无关延时替代修复 |
| 最小修复 | 仅修改产生根因的模块；跨端共享逻辑必须验证两端调用方 |
| 自动化补测 | 能在 jsdom、Python、Rust 或原生测试中稳定复现的缺陷必须补回归测试 |
| 定向复测 | 复测原始步骤、失败分支、快速重复操作和取消分支 |
| 影响回归 | 按变更范围执行关联页面矩阵；全局导航、存储、主题、路由改动须回归阶段 1 与全部受影响页面 |

## 四、缺陷分级与发布门槛

| 等级 | 定义 | 处理要求 |
|---|---|---|
| P0 | 无法启动、数据丢失、隐私或安全风险、核心页面不可用 | 立即阻断测试与发布，修复后全量回归 |
| P1 | 核心流程失败，例如无法保存、导入导出失败、同步错误、按钮无响应 | 当前迭代必须修复，修复后执行所属阶段和数据链路回归 |
| P2 | 非核心功能异常、跨端行为不一致、可恢复的显示或交互错误 | 记录并排期，发布前完成风险评估和定向复测 |
| P3 | 文案、轻微视觉或低频体验问题 | 集中修复，避免阻塞 P0/P1 闭环 |

**发布准入：** 不存在未关闭 P0/P1；阶段 0 自动化基线通过；所有页面均有按钮矩阵记录；高风险数据、同步、导入导出、容器和安装包链路完成对应验收；所有已修复缺陷均有复测证据。

## 五、自动化演进建议

1. **优先补齐启动与路由测试。** 为 `main.js`、PC/移动路由建立端类型判定、动态加载、历史栈和异常重试测试，先锁定全局入口风险。
2. **引入浏览器端到端测试。** 单独立项接入 Playwright，以固定数据、固定视口和 `?ui=pc` / `?ui=mobile` 覆盖阶段 1 与阶段 2 的 P0/P1 按钮；不在首次接入时加入易波动的全量截图比对。
3. **为控件建立可审计清单。** 在端到端测试目录维护“页面—控件—用例编号”映射；新增按钮必须同时新增或更新映射与测试，避免以后再次遗漏。
4. **补强原生存储测试。** 为 `sqlite-storage.js` 的 CRUD、迁移、失败回滚和图片一致性建立隔离测试；Android 端补充权限、保存图片、返回键和生命周期业务测试。
5. **接入持续集成门槛。** 提交合并前至少执行前端、Python、Rust 测试与生产构建；端到端冒烟在主分支或发布候选版本执行，并设置覆盖率趋势监控而非仓促设定不可信阈值。
6. **先修正文档漂移。** `docs/README.md` 的版本和目录示例已与当前入口结构不一致；在本计划实施时同步更新，避免测试人员依据过期入口执行。
