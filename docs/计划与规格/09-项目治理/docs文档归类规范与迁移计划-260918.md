# docs 文档归类规范与迁移计划-260918

> 类型：项目治理 · 文档体系重构
> 范围：仅 `docs/` 目录结构、命名与索引；不改业务源码逻辑
> 前置阅读：`docs/导航/apps-code-map.md`、`docs/工程指南/工程目录说明.md`、`docs/README.md`

---

## 一、目标

1. 建立**稳定、互斥、可导航**的 `docs/` 一级分类规范。
2. 消除「设计 vs UI 计划」「技术 vs 模块」「经验 vs 修复记录」等边界重叠。
3. 把已完成/过期材料统一进历史归档，活跃区只保留当前有效文档。
4. 统一文件命名与日期格式，降低查找成本。
5. 重写入口索引（`docs/README.md`、`apps-code-map.md`、各子目录 README），并同步脚本/技能中的硬编码路径。

**非目标**：不清理 `UI设计稿/` 旁支源资产；不改 Python/Tauri/Capacitor 运行时；不删除任何有回溯价值的历史文档。

## 二、现状问题诊断

### 2.1 一级分类重叠、职责不清

| 现状目录 | 问题 |
| --- | --- |
| `设计文档/` | 既放全局设计系统（UI/UX、主题 Token），又放组件复刻稿、生图提示词资产、会话交接摘要——职责混杂 |
| `UI计划/` | 与 `设计文档/` 边界模糊；内部又有 `PC端/` 与 `PC端UI设计/` 近似并列 |
| `技术文档/` vs `模块说明/` | 平台架构说明 vs 就近模块说明，索引未讲清「何时写哪边」 |
| `工程文档/` vs `工程目录整理/` | 目录整理方案本质是治理计划，应归计划/归档，不应与交接文档平级 |
| `项目开发经验/` vs `已修复问题/` vs `对话历史/` | 三类「事后沉淀」边界不清，查找时需三处翻 |
| `计划文档/` vs `compose/spec/` | compose 规格未纳入主分类导航，活跃计划索引也不指向它们 |
| `测试记录/` | 未写入 `docs/README.md` 文档索引，入口不可见 |
| 顶层散落文件 | `版本发布与更新记录维护指南.md` 应属版本域；`项目代码百科.md` 与 `apps-code-map.md` 职责重叠未裁定 |

### 2.2 归档不彻底

- `计划文档/` 活跃区仍保留大量早于 2026-07 且功能已落地的计划（如 v2.5.1/v2.6.0 移动端计划、搜索栏新拟态-260709 等），活跃索引失真。
- `工程目录整理/` 整目录为一次性治理方案与过程笔记，应整体归档。
- `测试记录/` 中 2605xx 历史验收记录与「活跃测试」混放。
- `设计文档/` 中 `首页挂机植物-会话交接摘要.md`、早期 4 阶段生图提示词等属过程材料，应降级归档。

### 2.3 命名不统一

| 维度 | 现状 | 问题 |
| --- | --- | --- |
| 语言 | 中英混用（`api-reference.md` vs `PC端安装包构建方案.md`） | 检索与心智负担 |
| 日期 | 部分 `-YYMMDD`、部分无日期、部分 `vX.Y.Z-` 前缀 | 无法一眼判断新旧 |
| 页面序号 | `UI计划/PC端/03-提示词详情.md` 与 `03-提示词详情-可爱治愈风.md` 并存 | 版本关系不明 |
| 索引文件 | 有的目录有 README，有的只有分类索引，有的都没有 | 入口不一致 |

### 2.4 索引过时

- `docs/README.md` 仍标注「版本 2.2.1 / 最后更新 2026-05-04」，实际版本已到 v2.5.9+。
- 该索引缺少：`模块说明/`、`测试记录/`、`compose/`、`项目代码百科.md`、`工程目录整理/`、`assets/`。
- `设计文档/README.md` 仅列 3 条，目录实际 15+ 文件。
- `工程目录说明.md` 中 docs 推荐分类未覆盖 `测试记录`、`compose`、`项目代码百科`。

### 2.5 外部硬编码路径（迁移约束）

以下路径被脚本/技能/首页 README **写死**，迁移时必须同批改或**刻意保留原路径**：

| 引用方 | 硬编码路径 | 建议策略 |
| --- | --- | --- |
| `README.md`（仓库根） | `docs/assets/readme/*`、`docs/README.md`、`docs/导航/apps-code-map.md`、`docs/技术文档/*`、`docs/构建方案/README.md`、`docs/版本记录/changelog.md` | **资产与技术文档/构建方案/版本记录路径尽量保持**；若改名则同批改 README |
| `scripts/publish_release.ps1` | `docs/版本记录/changelog.md` | **保留 `docs/版本记录/` 目录名**，或同批改脚本 |
| `scripts/gen_release_body.py` | 同上 | 同上 |
| `scripts/backfill_release_notes.py` | 同上 | 同上 |
| `.mimocode/skills/release-publish/SKILL.md` | `docs/版本记录/changelog.md`、`docs/版本记录/更新记录规范.md` | 同上 |
| 计划/compose/模块文档交叉引用 | 大量相对路径 `docs/设计系统/*`、`docs/模块说明/*` 等 | 迁移后批量校验修正（历史归档内旧路径可保留并在归档 README 说明） |

**结论**：`docs/版本记录/`、`docs/assets/`、`docs/技术文档/`、`docs/构建方案/` 四条路径优先保持稳定；其余允许在规范下重组。

## 三、目标分类规范（新体系）

### 3.1 设计原则

1. **按「文档生命周期 × 职责」分一级目录**，不按「写作者」或「功能模块」堆文件。
2. 一级目录数量控制在 **8～10 个**；宁可合并，不要碎片。
3. 每个一级目录必须有 `README.md` 索引，并写清「放什么 / 不放什么」。
4. 过程性、一次性、已完成材料 → `_归档/`；**活跃区永不堆历史**。
5. 导航类文件（地图、百科）单独成区，不与业务文档混放。

### 3.2 推荐目录结构

```text
docs/
├── README.md                          # 文档中心总入口（重写，含版本与全量导航）
├── 导航/                               # 全局地图与百科
│   ├── apps-code-map.md               # 文件导航与更新落点（原位置可软链说明，正文迁入）
│   └── 项目代码百科.md
```

### 3.3 一级目录职责边界（放什么 / 不放什么）

| 目录 | 放什么 | 不放什么 |
| --- | --- | --- |
| `导航/` | 全局代码地图、项目百科 | 具体模块/API 说明 |
| `工程指南/` | 交接、迁移、目录职责、发版维护流程 | 具体版本 changelog、单次构建步骤细节 |
| `技术文档/` | 平台架构、API、同步协议、脚本技术链路 | 页面 UI 方案、模块使用说明 |
| `设计系统/` | 主题 Token、全局组件规范、按钮/光标等设计语言 | 单页布局稿、生图提示词 |
| `页面与UI/` | 按端/页面的 UI 方案、复刻设计稿 | 全局 Token 定义、已实现模块的代码说明 |
| `模块说明/` | 单模块职责、文件清单、交互边界（就近、短） | 完整平台架构、发版记录 |
| `构建方案/` | 各端打包流程与产物说明 | 发版变更内容（归版本记录） |
| `版本记录/` | changelog 权威源 + 更新说明格式规范 + 版本索引 | 功能设计细节 |
| `计划与规格/` | **未完成或需续作**的实施计划；compose 功能规格 | 已完成计划（进 `_归档/计划/`） |
| `质量与复盘/` | 测试记录、已修复问题复盘 | 下一次要做的测试计划（归计划 07） |
| `素材与提示词/` | 生图提示词、美术素材对照表 | UI 设计规范 |
| `_归档/` | 已完成/过期/一次性材料 | 仍在维护的规范与活跃计划 |

**判定口诀**（写新文档时用）：

1. 还要做吗？→ 是：`计划与规格`；否且有价值：`_归档` 对应子类。
2. 讲「怎么构建/怎么发版」？→ `构建方案` / `工程指南`。
3. 讲「系统长什么样」？→ `设计系统`（全局）或 `页面与UI`（单页）。
4. 讲「某模块代码在哪、干什么」？→ `模块说明`。
5. 讲「测过什么 / 修过什么」？→ `质量与复盘`。
6. 是画图用的提示词/素材词？→ `素材与提示词`。

## 四、命名规范

### 4.1 目录名

- 一级目录使用**中文**，不加数字前缀（避免「第 N 次整理」后序号失效）。
- 归档目录固定为 `_归档`（下划线前缀，排序置顶、语义明确）。
- 计划与规格下的分类子目录**保留现有 `01-`～`10-` 编号**（已有索引与心智习惯，改动收益低）。

### 4.2 文件名

统一格式：

```text
[范围前缀]-主题-可选版本或日期.md
```

| 规则 | 说明 | 示例 |
| --- | --- | --- |
| 语言 | **新文档优先中文主题**；已有稳定英文技术文档名可保留，但须在 README 中给出中文职责说明 | `api-reference.md` 可保留 |
| 日期后缀 | 过程类文档（计划/测试/治理）必须带 `-YYMMDD` | `PC端样式文件拆分治理计划-260716.md` |
| 规范/架构类 | 长期有效文档**不带日期**，在文首用 `> 最后更新：` 元信息 | `跨端配色与主题令牌规范.md` |
| 版本前缀 | 仅版本发布相关计划/记录使用 `vX.Y.Z-` | `v3.0.0-PC端UI完全重构计划.md` |
| 禁止 | 空格、连续下划线、无语义缩写（`plan.md`、`notes.md`） | — |
| 页面序号 | 页面 UI 文档用两位序号 + 主题；变体用后缀标明关系 | `03-提示词详情.md`、`03-提示词详情-可爱治愈风变体.md` |

### 4.3 索引文件

- 每个一级目录必须有 `README.md`。
- `计划与规格/` 可额外保留 `计划文档-分类索引.md`（或更名为 `分类索引.md`），但 **README 必须能独立导航**。
- 文档中心 `docs/README.md` 顶部固定元信息：`> 文档版本：YYYY-MM-DD | 对应应用版本：vX.Y.Z`。

## 九、风险与回滚

| 风险 | 缓解 |
| --- | --- |
| 交叉引用断裂 | 分阶段迁移 + 每阶段 `rg` 扫描；优先保留脚本敏感路径 |
| 发版脚本找不到 changelog | **不改** `docs/版本记录/` 目录名 |
| 历史计划被误判为可下沉 | 阶段 0 对照 changelog 与 Git 逐条确认；有争议的标「待确认」暂留活跃 |
| 大量 Git rename 导致 diff 噪音 | 使用 `git mv`；迁移提交与「内容修改提交」分开 |
| 中文路径在部分工具链显示异常 | 项目已长期使用中文目录，风险低；保持 UTF-8 |
| 归档后仍被搜索命中造成过时结论 | `_归档/README.md` 声明「非现行规范」；正文顶部可加 `> 状态：已归档` |

**回滚**：迁移以独立 Git 提交进行；任一阶段失败可 `git revert` 该阶段提交，不混入功能代码提交。
